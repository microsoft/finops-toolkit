# AI costs and tokenomics

Load this reference for questions about Microsoft Foundry, GitHub Copilot, Microsoft 365 Copilot or Copilot Studio costs. These are investigation and decision rules, not a price list, an entitlement promise or proof of connected telemetry. The rules in `SKILL.md` still apply.

1. Classify the product first. Establish the plan, license entitlement, deployment, agreement, cloud and billing model only as far as they change the answer, one blocking variable at a time. Distinguish model token telemetry, GitHub AI Credits, Copilot Credits, licenses, provisioned throughput units (PTUs) and metered service charges. Define the unit from applicable documentation instead of assuming a conversion between them.
2. For the GitHub Copilot developer product, retrieve the current official GitHub billing and plan documentation. Check whether the account is on a current or legacy billing model, including documented transition dates. Don't assume premium requests remain the billing basis, and don't invent a fixed allowance or credit-to-token rate. Don't reject a current documented price just because it differs from stored knowledge. Keep developer-product billing separate from Copilot Studio's GitHub Copilot harness.
3. For Foundry, check the actual model, version, region and deployment type. Consider documented input, output and cached-token charges, provisioned capacity and batch where supported, plus retrieval or search, storage, observability, orchestration, tool calls, failures and retries within the chosen cost boundary. Check whether each component is already included before adding it, to avoid double counting. Don't promise a token breakdown unless the necessary telemetry is available. Compare quality, latency and cost with representative measured workloads, and don't claim a universally best model or a universal PTU break-even point.
4. For Microsoft 365 Copilot and Copilot Studio, check the licensed, included and consumption-based scope, user entitlement and workload. Don't treat an included capability as universally free, assume a license covers every agent or scenario, or translate a license into a fixed token allowance without explicit applicable evidence.
5. Label every cost result Estimate, Measured or Invoiced, with currency, period, units, scope, source dates, assumptions, the cost boundary and what's excluded. A usage meter multiplied by a rate is an estimate unless billing evidence establishes otherwise. Use actual billing records for an Invoiced label, and apply Invoice reconciliation from `references/accuracy-checks.md`.
6. Prefer cost per successfully completed, quality-approved task: attributable cost within the stated boundary, including failed attempts, retries and relevant infrastructure, divided by tasks that meet the stated success and quality criteria. Define the denominator, avoid double counting, and report workload, service and team aggregates rather than ranking individuals.
7. Calculate with a computation tool when one is available and appropriate for the data's privacy. Otherwise show transparent arithmetic, units and assumptions, and don't claim code ran. Use ranges and sensitivity checks when workload, rate or success assumptions are uncertain, and mark hypothetical rates as hypothetical.
8. Treat budgets, alerts, quotas, concurrency or token limits and spend controls separately for each product and plan. Explain whether each is observational, notification-based or enforced, with exact evidence. Don't call a budget a hard stop or promise a hard cap without the documented conditions. Advise on controls; don't change them, buy capacity or start an automated action.
